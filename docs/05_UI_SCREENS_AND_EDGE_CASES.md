Every required edge case is documented below with **Scenario & Trigger**, **Expected System Behavior**, and **Recovery & Audit Path**.

| # | Edge Case Scenario | Expected System Behavior & Technical Resolution |
| :--- | :--- | :--- |
| **EC-01** | **Two customers at the same table scan the same table QR code** | Both browsers resolve `/q/{qr_token}` and receive valid `customer_session_token` cookies bound to that `table_id`. While the table is `AVAILABLE`, neither scan marks the table `OCCUPIED`. Once the first order is placed, both browsers subscribe to `room:table_session:{id}` and see live order statuses and the shared ₹5,000 session limit (subject to policy choice in **DR-01**). |
| **EC-02** | **Two people (or Customer + Waiter) submit an order for the same table simultaneously** | `POST /orders` acquires a PostgreSQL row-level lock (`SELECT ... FROM restaurant_tables WHERE id = :id FOR UPDATE`). Transaction A executes first: if table was `AVAILABLE`, it creates the single `ACTIVE` `TableSession` (enforced by partial unique index `idx_one_active_session_per_table`) and inserts Order #1. Transaction B unblocks 5ms later, sees the table is now `OCCUPIED`, attaches Order #2 to the **same** `active_session_id`, and validates `(Order #1 + Order #2) <= ₹5,000`. |
| **EC-03** | **Duplicate order submission (double-tap on "Place Order")** | Client disables button on first tap and sends a UUIDv4 `Idempotency-Key` header. If two requests reach FastAPI, the unique constraint on `orders.idempotency_key` catches the second request and returns the exact HTTP `201` response of the first order. Even if the client generated a new key by mistake, the **15-second identical cart-hash debounce** rejects the duplicate (`429 DUPLICATE_ORDER_DETECTED`). |
| **EC-04** | **Internet disconnect during order submission** | Client times out without knowing if the server committed the order. When connectivity returns, the client retries `POST /orders` using the **exact same `Idempotency-Key`**. If the first request succeeded, the server returns the existing order without duplicating it; if it never reached the server, it creates the order cleanly. |
| **EC-05** | **Customer closes browser tab after ordering and reopens / rescans QR** | The signed `customer_session_token` (stored in `HttpOnly` cookie + `localStorage` session backup) persists for the duration of the active `TableSession`. Reopening the browser or rescanning the table QR automatically restores the active `TableSession` and displays all live order statuses on `CW-8`. |
| **EC-06** | **Customer refreshes the web page mid-session** | Unsubmitted cart state is preserved in `sessionStorage` (keyed by `qr_token`), while active submitted orders and current outstanding balance are fetched fresh from `GET /api/v1/public/session/orders` and re-subscribed via WebSocket. |
| **EC-07** | **Customer session token (`customer_session_token`) expires** | If the customer scanned the QR and left the browser idle for $>30$ minutes without placing an order, the token expires. Submitting an order returns `401 SESSION_TOKEN_EXPIRED`, prompting the customer to re-scan the table QR (or auto-refreshing if the QR URL is still in the address bar). |
| **EC-08** | **QR token is revoked by Admin while customer is browsing** | Every customer API call (`POST /orders`, `GET /session/orders`) checks `table_qr_tokens.status == 'ACTIVE'`. Once revoked, any subsequent action returns `410 QR_TOKEN_REVOKED` and displays: `"This table's QR code has been deactivated. Please ask a waiter for assistance."` |
| **EC-09** | **Customer photographs QR code and tries to order from home later** | Mitigated by: 1) Operating hours gate (blocked when restaurant is closed), 2) Existing session token revocation on previous bill completion, 3) Waiter receives instant `"First QR Order on Table X"` alert when an `AVAILABLE` table transitions to `OCCUPIED` (allowing 1-tap rejection if table is physically empty), 4) If table is currently occupied by real guests with an `ISSUED` bill, QR orders are locked, and 5) Admin can regenerate the table's QR token in 1 click, permanently invalidating the photograph. |
| **EC-10** | **Table is already `OCCUPIED` when a new customer scans the QR (e.g., previous guests left without waiter closing session, or second guest at same table)** | If a bill is already `ISSUED` for the occupied table, the UI shows `"Bill in progress for this table — please ask your waiter to reset the table."` If the session is active and no bill is issued yet, behavior follows **DR-01** (either allows table companions to add orders with real-time notifications to the table session & waiter, or restricts ordering to the initiating device unless unlocked by waiter). |
| **EC-11** | **Customer tries to order from an occupied table after the bill has been generated (`ISSUED`)** | Generating a bill sets `table_sessions.is_qr_ordering_locked = true`. Any customer QR order attempt returns `423 TABLE_BILL_ALREADY_ISSUED`: `"Your bill has already been prepared. Please speak to your waiter if you wish to order additional items."` |
| **EC-12** | **Menu item or variant becomes unavailable while sitting in the customer's or waiter's cart** | 1) Live `MENU_AVAILABILITY_UPDATED` WebSocket event immediately flags the item in the open Cart UI as `"Just Sold Out — Remove to proceed"`.<br>2) Even if the WebSocket event was missed, `POST /orders` re-verifies `is_available = TRUE` inside the DB transaction and returns `409 ITEM_UNAVAILABLE` with the exact unavailable item name(s). |
| **EC-13** | **Admin changes an item's price while the item is in a customer's cart** | When the customer taps "Confirm Order", the backend compares the current `menu_price_variants.price` with the cart's displayed price (or always uses authoritative DB price). Recommended UX: Customer Cart sends `expected_unit_price` for each line; if Admin just changed the price, `POST /orders` returns `409 PRICE_UPDATED` (`"Price of Chicken Biryani Full updated from ₹180 to ₹200. Please review updated cart total"`), updating the cart UI so the customer confirms the exact price they will be charged. Once `PLACED`, historical price snapshots on `order_items` never change. |
| **EC-14** | **Kitchen wants to reject only ONE unavailable item in a multi-item `PLACED` order** | Kitchen can either: 1) Reject the entire `PLACED` order with reason `"Chicken Kebab out of stock — please reorder other items"`, OR 2) Coordinate with the Waiter (or use partial item cancellation if enabled) to cancel just the unavailable line item via `OrderModificationEvent` and accept the remaining items. |
| **EC-15** | **Kitchen rejects an entire `PLACED` order** | Kitchen provides mandatory `rejection_reason`. Order transitions `PLACED -> REJECTED`. Order subtotal is subtracted from `table_sessions.current_outstanding_amount`. Customer and Waiter receive instant `ORDER_REJECTED` alert with reason. If this was the only active order in the `TableSession`, the session closes (`CLOSED_NO_CHARGE`) and the table automatically reverts from `OCCUPIED` to `AVAILABLE`. |
| **EC-16** | **Kitchen taps "Accept" at the exact same moment Waiter submits an "Edit Order" on a `PLACED` order** | Both operations lock the `orders` row (`SELECT ... FOR UPDATE`) and validate `expected_version`. Whichever transaction commits first increments `orders.version` from `1` to `2`. The second transaction fails the version check and receives `409 ORDER_VERSION_CONFLICT`, refreshing the UI with the latest state so neither staff member overwrites the other blindly. |
| **EC-17** | **Customer wants to cancel an order after Kitchen has already accepted it (`ACCEPTED`)** | Customer QR Web UI disables self-service cancellation once status is $\ge$ `ACCEPTED` and displays: `"Your order has been accepted by the kitchen. Please call a waiter immediately if you need to make changes."` Waiter can cancel an `ACCEPTED` (not yet `PREPARING`) order with a mandatory reason, which triggers an urgent audio/visual alert on the Kitchen KDS. |
| **EC-18** | **Cancellation is requested when food is already `PREPARING`, `READY`, or `SERVED`** | Because ingredients are already being cooked or plated, neither the Customer nor a regular Waiter can unilaterally cancel the order in the app. Only an **Admin** can execute a cancellation/void on a `PREPARING`, `READY`, or `SERVED` order, which requires a mandatory `cancellation_reason` and an explicit `is_wastage = true/false` flag recorded in `order_modification_events` and `audit_logs`. |
| **EC-19** | **Waiter accidentally selects the wrong table number and places an order** |- If the order is still `PLACED` or `ACCEPTED`, the waiter can immediately cancel the order with reason `"Entered wrong table number"`. If the wrong table had no other orders, cancelling it automatically reverts that wrong table from `OCCUPIED` back to `AVAILABLE`.<br>- Admin can also reassign/move an active order or session to the correct table via an audited `TRANSFER_TABLE` action. |
| **EC-20** | **Waiter records payment, backend commits `PAID`, but Waiter's phone loses Wi-Fi/4G before receiving HTTP 201** | Waiter's Flutter app retries `POST /api/v1/waiter/bills/{bill_id}/payments` with the same `Idempotency-Key` upon reconnection (or refreshes the table view), receiving the committed `PAID` receipt cleanly without recording a double payment. |
| **EC-21** | **Two waiters try to record payment for the same bill twice** | Enforced at three levels: 1) Row-level lock on `table_sessions` and `bills`, 2) Check `bills.status == 'ISSUED'` (second request fails with `409 BILL_ALREADY_PAID`), and 3) Session completion atomically closes the table session on the first payment. |
| **EC-22** | **Customer payment fails (e.g., UPI app timeout or declined card at physical terminal)** | Waiter only taps "Confirm Payment Received" after verifying payment success (or records a `FAILED` payment attempt log if tracking failed tries). If payment fails, `bills.status` remains `ISSUED`, `table_sessions.status` remains `ACTIVE`, and the waiter can select an alternate payment method (e.g., `CASH`). |
| **EC-23** | **Two waiters try to generate a bill for the same table simultaneously** | Protected by `SELECT ... FROM table_sessions FOR UPDATE` and the PostgreSQL partial unique index `idx_one_active_bill_per_session ON bills(table_session_id) WHERE status IN ('ISSUED', 'PAID')`. The second waiter receives `409 BILL_ALREADY_ISSUED` and is shown the existing generated bill. |
| **EC-24** | **Two waiters edit the same order on the same table simultaneously** | Optimistic concurrency control (`expected_version` on `orders`) ensures the second waiter's conflicting edit is rejected with `409 ORDER_VERSION_CONFLICT`, showing the first waiter's just-saved changes before allowing further edits. |
| **EC-25** | **Two Admin users (or staff) toggle menu item availability simultaneously** | Last committed atomic `UPDATE` wins, increments item version, writes chronological `audit_logs` entries for both actors, and broadcasts the final authoritative `MENU_AVAILABILITY_UPDATED` state to all connected WebSocket clients. |
| **EC-26** | **Restaurant temporarily closes mid-day (e.g., Afternoon break 3:30 PM – 6:30 PM or emergency)** | Admin toggles `is_restaurant_open = false` (or `is_qr_ordering_enabled = false`). New QR scans and new Customer QR order submissions are immediately blocked with a polite `"We are currently closed for new QR orders"` banner, while existing `OCCUPIED` tables can still have their in-progress orders served, billed, and paid by waiters. |
| **EC-27** | **A physical table needs maintenance / is broken or reserved for repair** | Admin sets `restaurant_tables.status = 'DISABLED'` (only allowed when table has no active session). Any scan of that table's QR code returns `403 TABLE_UNAVAILABLE` (`"This table is currently out of service"`), and the table is greyed out on the Waiter floor grid. |
| **EC-28** | **Physical QR sticker on a table is scratched/damaged and unreadable by customer phone** | Customer calls waiter verbally. Waiter takes the table's order using the Waiter Flutter App (`WM-5`/`WM-6`) via short item codes (`CB-F`). The table transitions to `OCCUPIED` and operates normally while Admin prints a replacement QR sticker from `AW-8`. |
| **EC-29** | **Old QR code is scanned after Admin regenerated the table's QR** | The old token exists in `table_qr_tokens` with `status = 'REVOKED'`. Scanning it returns HTTP `410 Gone` and renders `CW-9`: `"This QR code has been replaced. Please scan the updated QR code on your table or call a waiter."` |
| **EC-30** | **Table session reaches or exceeds the ₹5,000 outstanding order limit** | When `current_outstanding_amount (₹4,850) + new_order (₹300) = ₹5,150 > ₹5,000`, `POST /orders` rejects the order (`422 OUTSTANDING_LIMIT_EXCEEDED`). Customer Web displays: `"Maximum active order limit of ₹5,000 reached (Current: ₹4,850). Please call a waiter to assist with your order or settle an interim bill."` Admin can also raise the session's `custom_max_outstanding_limit` for large group tables. |
| **EC-31** | **Customer triggers rate limiting (e.g., >3 orders in 2 minutes or >3 unaccepted `PLACED` orders)** | API returns `429 RATE_LIMIT_EXCEEDED` with `retry_after_seconds`. Customer UI displays: `"You have several recent orders awaiting kitchen confirmation. Please wait a moment or call a waiter to add more items."` |
| **EC-32** | **Suspicious ordering behavior detected on a table (repeated rejected orders or rapid rate-limit violations)** | System automatically sets `table_sessions.is_qr_ordering_locked = true`, creates a high-priority notification for Waiter & Admin (`"Suspicious QR activity on Table 7"`), and blocks further QR orders on that session until a Waiter physically checks the table and taps **"Unlock QR Ordering"** (or Admin regenerates the QR). |
| **EC-33** | **All orders in an `OCCUPIED` table session are rejected by Kitchen or cancelled before any food is prepared** | When the last remaining active order in a `TableSession` transitions to `REJECTED` or `CANCELLED` (leaving `0` non-cancelled/non-rejected orders), the state engine automatically transitions `table_sessions.status -> 'CLOSED_NO_CHARGE'`, sets `restaurant_tables.status -> 'AVAILABLE'`, clears `active_session_id = NULL`, and broadcasts `TABLE_AVAILABLE` so the table is not stuck as occupied. |
